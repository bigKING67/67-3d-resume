# 作品叙事与媒体系统

本文负责作品栏目封面、详情内容、Hero、正文媒体、图文排版和真实性标注。产品目标以 [`../PRODUCT.md`](../PRODUCT.md) 为准，色彩、字体、表面与运动以 [`../DESIGN.md`](../DESIGN.md) 为准；这里不建立第二套产品或视觉权威。

## 核心原则

作品详情不是仓库 README 的缩写，也不是截图仓库。它要让招聘者、潜在合作者和同行快速回答：项目服务谁、解决了什么、六七做了什么、关键取舍是什么，以及为什么应该相信这些描述。

- **先有主张，再有图片。** 图片数量由重要主张和可用证据决定，不设固定下限、上限或三图模板。
- **承诺后紧跟证明。** 抽象结论后尽快给真实界面、产物、系统关系、过程或可复现证据。
- **一个媒体，一个主要判断。** 同一判断不要换皮重复；一张总图无法读懂时就拆开。
- **项目结构可以不同。** 完整性由读者问题决定，不由统一章节名决定。
- **事实边界可见。** 真实运行、源码事实、脱敏产物、系统示意、概念插图和产品规划不能混写。

## 上游参考边界

上游在线预览 [`about.senbuzy.com`](https://about.senbuzy.com/) 与 [`dayinji/sen-3d-resume`](https://github.com/dayinji/sen-3d-resume) 只承担 `structure` 参考角色。2026-09-02 的审计表明：原版使用独立栏目封面、项目 Hero、角色/标签和按故事需要排列的图片、视频、嵌入内容；不同项目的媒体数量和形式并不相同。

本项目只吸收这些机制：

- 栏目封面、项目 Hero、元信息和正文媒体各司其职；
- 媒体跟随项目内容，而不是让项目套进同一媒体模板；
- 产品用界面证明，互动作品用过程和交互证明，技术系统用结构、运行产物和验证证明；
- 桌面与窄屏分别考虑信息优先级。

上游作者的个人文案、图片、视频、品牌、奖项、数据和独特作品构图不进入本项目。完整来源和选择性吸收记录见 [`../UPSTREAM.md`](../UPSTREAM.md)。

## 从主张到账本

写正文前，先在项目内容计划或草稿中列出这些字段：

| 字段 | 要回答的问题 |
| --- | --- |
| 读者问题 | 读者看完这一节应该理解什么？ |
| 核心主张 | 本项目真正要表达的价值、能力或区别是什么？ |
| 本人职责 | 六七负责了哪些判断、设计或实现？ |
| 事实来源 | 当前源码、运行页面、文档、真实产物、脱敏案例还是外部权威来源？ |
| 证据等级 | 真实运行、真实截图、源码事实、脱敏产物、确定性示意还是规划？ |
| 最佳媒介 | 文字、截图、流程、架构、对比、数据、短视频还是概念插图？ |
| 公开边界 | 是否需要脱敏，是否包含客户、账号、内部路径、凭据或实时数据？ |
| 决定 | `text / keep / adapt / split / replace / reject` |

只有当视觉表达明显优于文字时才增加媒体。媒体不是内容完成度的计数器。

## 可选择的叙事维度

以下是候选维度，不要求每篇齐全，也不要求每个维度配一张图：

1. 对象与场景：给谁用，在什么任务里使用。
2. 问题与摩擦：旧方式为什么低效、模糊、危险或不可复核。
3. 价值变化：项目让什么事情从什么状态变成什么状态。
4. 本人职责：六七负责的判断、产品设计、工程实现或经营决策。
5. 系统与流程：组件、角色、状态、数据流和生命周期如何协作。
6. 关键能力：最值得展示的功能、机制或工作流。
7. 工程难点：兼容、安全、性能、可靠性、权限、部署或可复现性。
8. 关键取舍：为什么这样设计，放弃了什么，如何处理冲突。
9. 实际体验：真实界面、操作路径、响应式状态和交互反馈。
10. 结果与证据：真实产物、验证回执、数据结果、案例或复现路径。
11. 边界与成熟度：已落地、受控验证、产品规划、未验证和下一步。

正文优先选择最能体现项目差异、本人判断和可信度的维度。

## 内容结构

成熟案例通常需要回答以下问题，但章节可以合并、拆分并使用项目自己的标题：

1. **一句话承诺**：它是什么、服务谁、改变什么。
2. **本人角色与成熟度**：做了什么，当前处于什么状态。
3. **问题或机会**：为什么值得解决。
4. **方法与关键决策**：系统、产品或创意如何成立。
5. **项目独有的深度部分**：一个或多个最值得记住的能力、难点或取舍。
6. **结果与证明**：用真实产物、运行状态、数据或确定性证据支持结论。
7. **边界与下一步**：哪些没有做、没有验证或不能公开。

不要把这些问题机械改写成七个固定标题。例如 Review Craft 可以写“一条 Finding 怎样成立”，Creative Craft 可以写“为什么淘汰另外两条路线”，browser67 可以写“页签也有所有权”。

## 行文规则

- 结论在前，解释在后；一个段落只处理一个主要判断。
- 使用第一人称说明本人职责，不把团队成果全部归到个人。
- 多用“定义、拆分、验证、实现、取舍、交付”等具体动词。
- 避免“赋能、领先、极致、智能化升级”等无证据包装词。
- 数字必须带时间、口径、范围和来源；不把示例分数写成实际经营效果。
- 区分事实、推断、观点、计划和未验证项。
- 源码存在、构建通过、本地可见、线上可用和生产效果是不同证据层。
- 仓库 README 负责完整安装与技术说明；简历详情负责价值、本人职责、关键取舍和可信证据。

## 媒体选择

### 什么时候应该用图

一张图至少满足一个条件：

- 展示文字难以描述的空间、流程、状态或组件关系；
- 证明真实产品、真实作品或真实产物存在；
- 比较改变前后、候选方案或关键取舍；
- 把复杂系统拆成可理解的局部；
- 支撑一个决定项目可信度的核心主张；
- 展示交互、运动、视觉作品或数据结果。

### 什么时候应该删图

- 只是把相邻段落重新写进图片；
- 与另一张媒体承担相同结论；
- 只是通用节点图换了项目名和信号色；
- 实际展示时小字无法阅读；
- 没有事实来源，只能虚构界面、指标或回执；
- 视觉好看但不能帮助理解项目；
- 一张图承担过多判断且没有清晰阅读顺序。

### 媒体来源优先级

1. 真实产品界面、运行状态或作品；
2. 已脱敏的真实产物、报告、回执或案例；
3. 根据当前源码和已验证事实确定性绘制的图表、流程或结构图；
4. 用于解释抽象对象、场景和气质的生成式插画。

生成式图片主要用于栏目封面和 Hero。精确中文、命令、路径、指标、品牌字样、真实 UI 和验证回执不得交给图像模型自由生成。

### 证据标签

图注使用最接近事实的标签：

- `真实界面`：来自实际产品或运行页面；
- `脱敏产物`：真实材料经裁切、遮盖或替换敏感信息；
- `系统示意`：根据当前源码或已验证文档确定性绘制；
- `概念插图`：用于说明对象、场景或抽象关系，不承担运行证明；
- `产品规划`：尚未实现的方向，不得画成已上线界面。

## 媒体层级

| 层级 | 必须回答的问题 | 常见形式 | 禁止模式 |
| --- | --- | --- | --- |
| 栏目封面 | 这组作品共同代表什么？ | 能力地图、共同工作台、代表性组合画面 | 随机物件、单项目截图、密集总架构 |
| 详情 Hero | 这个项目是什么，最独特的对象或动作是什么？ | 工作场景、核心界面、结果导向构图 | 只写项目名、裁切完整架构图、复用栏目封面 |
| 正文媒体 | 这一处关键判断如何被看懂或证明？ | 界面、过程、结构、对比、数据、视频、产物 | 装饰图、重复图、伪造证据 |

栏目封面、详情 Hero 和正文媒体不得使用同一源图的简单裁切版本。相同材质、色彩和注释方式可以形成家族感，但画面主体和叙事职责必须不同。

## 图文节奏与版式

正文遵循“提出问题 → 给出媒体 → 解释应当看到什么”的节奏：

- 图片前说明它准备回答的问题；
- 图片后解释关键信息、来源、脱敏方式或未验证边界；
- 不在标题后立即塞图；
- 不把所有图片堆到文章末尾；
- 连续媒体必须承担不同判断；
- 长流程先给地图，再按需要给局部；
- 真实截图优先保持原始比例，不强行裁成统一 `16:9`。

正文支持四种布局：

| 布局 | 用途 | 桌面 | 窄屏 |
| --- | --- | --- | --- |
| `wide` | 架构、流程、宽界面 | 扩展到正文外侧 | 收回单列并保持可读 |
| `inset` | 报告、单张产品界面、局部证据 | 比正文略宽或等宽 | 单列 |
| `pair` | 前后、桌面/移动、两方案对照 | 两列 | 上下排列 |
| `sequence` | 步骤、创意路线、连续结果、短视频组 | 2–3 列或横向节奏 | 单列顺序阅读 |

简单单图继续使用 Markdown：

```md
![准确描述画面内容](./works/family/project-specific-name.webp)

_系统示意：根据当前源码绘制，说明……_
```

需要明确布局、图注或移动重排时使用本地 Markdown 已支持的 HTML：

```html
<figure data-layout="wide">
  <picture>
    <source media="(max-width: 640px)" srcset="./works/family/project-specific-name-mobile.webp" />
    <img src="./works/family/project-specific-name.webp" alt="准确描述画面内容" />
  </picture>
  <figcaption><strong>系统示意</strong>：根据当前源码绘制，说明……</figcaption>
</figure>
```

移动重排图是同一媒体的响应式版本，不重复计入内容节拍。只有信息需要重新编排时才制作移动版；照片、单一界面和可自然缩放的媒体可以共用一个文件。

## 视觉语言与规格

- 页面和详情弹层保持深炭蓝黑；正文媒体可以使用 DataHub 建立的暖白/浅灰编辑式“证据板”。
- 证据板使用深墨文字、发丝分隔、有限网格、克制噪点和项目自己的信号色，不演变成七套互不相干的风格。
- 一张证据板先确定一个主结论、主产物或主对比，再安排次级事实；不要把所有信息做成同尺寸、同权重的卡片网格。流程关系本身不重要时，不用通用节点图代替项目故事。
- Hero 先呈现对象、动作和结果关系；复杂架构留给正文。
- 真实截图只做必要裁切、脱敏和注释，不套设备壳或伪造产品界面。
- 不新增霓虹玻璃卡、彩色渐变墙、无意义 3D 图标或模板化“AI 大脑”。

| 用途 | 建议画布 | 说明 |
| --- | --- | --- |
| 栏目封面 | `960×640`（3:2） | 在作品卡尺寸下仍可理解 |
| 桌面 Hero | 约 `3.5–4:1` | 核心对象避开上下与两侧裁切区 |
| 窄屏 Hero | `1:1` 或内容需要的纵向比例 | 独立重排，不盲裁桌面图 |
| 宽流程 / 架构 | 1600–2400px 宽 | 按实际展示宽度检查文字 |
| 产品截图 / 报告 | 保留原始比例 | 不为统一比例破坏证据 |
| 短视频 | 最长边不超过 1920px | 提供 poster，默认静音 |

最终图片默认使用 WebP。单张超过约 `350 KiB` 时检查合理降采样、分图或压缩；不能为了文件小而牺牲证据文字的可读性。

包含精确文字、数字或状态的确定性图示应保留可重复生成的源文件；桌面与移动版必须来自同一事实模型，但允许按各自阅读顺序重新构图。只检查导出图片不能替代真实页面中的 `<picture>` 资源选择、布局与溢出验证。

资产使用项目语义命名，不再要求 `value / diagram / evidence`：

```text
web/public/works/<family>/
  cover.webp
  <slug>-banner.webp
  <slug>-mobile.webp
  <slug>-<specific-claim>.webp
  <slug>-<specific-claim>-mobile.webp
```

## AI Team Agent 边界

`AI Team Agent` 是栏目与产品总名，下面直接列出 `Pi SDK Agent`、`Team Agent`、`OpenViking`、`Work & Chat`、`Agent Governance`、`Deep Research` 六个系统。它们共同构成企业 Agent 的工作方式，但不能被折叠成 `Pi-67 Desktop` 的章节。

相关媒体可以按项目需要展示工作接力、Session、记忆、治理、研究计划、运行载体或证据层。状态词统一使用 `已落地`、`受控验证`、`产品规划`；测试或打包事实不冒充生产部署。

## 生产流程

1. 从当前仓库、真实产品和已验证材料列出事实、本人职责、可公开内容、敏感边界与缺失证据。
2. 建立主张账本，先决定每个重要判断最适合文字还是媒体。
3. 为栏目封面和 Hero 分别写一句“它必须让人看懂什么”。
4. 选择真实截图、脱敏产物、确定性图示或概念插图；没有证据时明确缺口。
5. 先做低保真信息构图，检查主体、阅读顺序和项目差异，再制作最终资产。
6. 输出必要的桌面与窄屏构图，检查裁切、文字、对比度、体积、脱敏和来源。
7. 写入 Markdown 后运行 `npm run validate:works`、`npm run lint`、`npm run build`。
8. 用 browser67 检查桌面和约 390px 窄视口的栏目卡、Hero、正文媒体、图注、关闭与外链。

## 验收清单

- [ ] 栏目封面在不读标题时仍能表达栏目共同能力。
- [ ] 每个重点项目有专属 Hero，未复用栏目封面或其他项目画面。
- [ ] 桌面与窄屏 Hero 的核心对象在真实裁切下成立。
- [ ] 每个重要主张都有合适的文字或媒体支持，不靠图片数量判断完整度。
- [ ] 每张媒体承担独立判断，且比相邻文字更有效。
- [ ] 项目之间没有只换名称和信号色的通用节点图。
- [ ] 示意图、真实截图、结果数据和计划状态没有混淆。
- [ ] 数据、账号、客户、路径和凭据已经脱敏；外部资产来源与边界清楚。
- [ ] 图片有准确 `alt`，图注说明证据类型与必要边界。
- [ ] 布局与 `DESIGN.md` 的暖白、炭蓝灰、发丝线、克制圆角和强调色一致。
- [ ] 桌面和约 390px 窄视口已在真实浏览器检查，截图样本与页面状态一致。
